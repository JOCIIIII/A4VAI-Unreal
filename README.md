# C-Track Sim (UE 5.8.2 + Cosys-AirSim 3.5.0 + PX4 v1.16 / Gazebo Classic)

Two maps, chosen with `CTRACK_MAP` (the same variable for Unreal, Gazebo and the map scripts):

| `CTRACK_MAP` | map | layout |
|---|---|---|
| `CTrack` (default) | the C-Track flight test field (A: path planning around tents, B: path following through a fan wind zone, C: collision avoidance between poles, a wall, a balloon figure and a crossing RC cart) | `layout/ctrack_layout.json` |
| `Yard` | a courtyard of the Inha University aerospace convergence campus (Songdo), built from a handheld SLAM lidar scan: trees with trunks and canopies, objects and ground relief as meshes made from the points, buildings as wall boxes. See [SLAM yard map](#slam-yard-map) | `layout/yard_slam_layout.json` |

Gazebo Classic does the dynamics (PX4 SITL, x8); Unreal + Cosys-AirSim renders and simulates the
lidar/cameras, fed with the vehicle pose by GazeboDrone (`ExternalPhysicsEngine`). Every obstacle
exists in both worlds at the same place: both are generated from one layout file
(`layout/ctrack_layout.json` or `layout/yard_slam_layout.json`).
Moving obstacles and the wind zone live in Gazebo (plugins); GazeboDrone mirrors the moving
obstacles onto Unreal actors of the same name.

```
layout/yard_slam_layout.json     Yard: walls, waypoints, mesh list (generated by slam_to_layout.py)
layout/slam_to_layout.py         SLAM point cloud -> yard layout + meshes (slam_meshes.py)
layout/slam/yard_map_points.ply  the yard scan (10 cm voxels, levelling and frames in the script)
layout/meshes/yard/              yard meshes: .obj for Gazebo, .glb for Unreal
layout/ctrack_layout.json        C-Track: waypoints, obstacles, RC cart, wind zone
layout/gen_gazebo_world.py       -> gazebo/worlds/ctrack.world (run by run_gazebo_px4.sh)
CTrackSim/                       Unreal project (maps /Game/CTrack/Maps/CTrack, .../Yard)
  Scripts/create_base_map.py       empty map, lights, PlayerStart at Start H (run once)
  Scripts/build_map_from_layout.py ground + layout into the map (rerunnable)
  Scripts/make_s900_pawn.py        optional vehicle look (model not included, see below)
gazebo/
  run_gazebo_px4.sh                gzserver + x8 + GazeboDrone + PX4 in container ctrack-sitl
  ctrack_sitl_entry.sh             what runs inside that container
  plugins/src                      wind zone and moving obstacle Gazebo plugins
patches/cosys-airsim/            our changes to Cosys-AirSim 5.8-v3.5.0 (applied by setup_deps.sh)
settings/                        AirSim settings (see below)
tools/fly_ctrack_check.py        offboard flight over the route with consistency checks
setup_deps.sh                    builds the plugin, GazeboDrone and the Gazebo plugins
package.sh                       builds the release assets (packaged Unreal build, Gazebo binaries)
```

## Requirements
- Ubuntu 22.04 (tested) with an NVIDIA GPU (Vulkan)
- [Unreal Engine 5.8.2 for Linux](https://www.unrealengine.com/linux) (Epic account; not
  redistributable) - only for the editor project; the release build runs without it
- cmake on the host for the editor project (Cosys-AirSim `build.sh`; without root, a release
  tarball extracted into `$DEPS_DIR/cosys-airsim-3.5.0/cmake_build/` is used too)
- Docker with `px4io/px4-dev-simulation-focal` (NVIDIA container toolkit for a fast gzclient)
- PX4-Autopilot v1.16 built for SITL with the gazebo-classic `x8` airframe (2000), laid out as
  `$PX4_WS/PX4-Autopilot/build/px4_sitl_default` (default `PX4_WS=~/Documents/A4VAI-SITL/PX4-Autopilot`)

## Setup without Unreal Engine (release build)
Download from the GitHub release and extract in the repository root:
```bash
mkdir -p packaged && tar -xzf CTrackSim-Linux.tar.gz -C packaged   # packaged/CTrackSim-Linux/
tar -xzf ctrack-gazebo-prebuilt.tar.gz                              # gazebo/bin, gazebo/plugins/build
```
`run_unreal.sh` then runs the packaged build (or set `CTRACK_PACKAGED=/path/to/CTrackSim-Linux`).
It uses Cosys-AirSim's default vehicle pawn. Instead of the prebuilt Gazebo binaries you can build
them without Unreal Engine: `./setup_deps.sh --gazebo-only`.

## Setup with Unreal Engine (editor project)
```bash
UE_ROOT=/path/to/Linux_Unreal_Engine_5.8.2 ./setup_deps.sh
```
Clones Cosys-AirSim `5.8-v3.5.0` into `~/Documents/InhouseSim-deps` (`DEPS_DIR`), applies
`patches/cosys-airsim`, builds AirLib with Unreal's bundled clang into `CTrackSim/Plugins/AirSim`
and the editor target, builds AirLib with gcc + GazeboDrone in the PX4 dev image
(`gazebo/bin/GazeboDrone`), and the Gazebo plugins (`gazebo/plugins/build`).
`./package.sh` builds the release assets from a clean clone (see the script).

## Run
```bash
./run_unreal.sh [settings.json]  # wait for the window / API port 41451
./gazebo/run_gazebo_px4.sh       # GUI=1 for gzclient, LAYOUT=other.json; logs in gazebo/logs/
# the yard: export CTRACK_MAP=Yard before both (C-Track is the default)
# PX4: MAVLink udp 14540 (offboard) / 14550 (GCS) on localhost
docker stop ctrack-sitl          # stop
```
The PX4 workspace is mounted read-only; PX4 runs in its own rootfs, so its parameters start from
the airframe defaults every run. The container uses the host network.

## Lidar scan pattern (Livox Mid-360)
With `"PatternFile"` the CPU lidar shoots a recorded shot sequence instead of its channel x
measurement grid (patch `0004`; `NumberOfChannels`, `MeasurementsPerCycle`, `RotationsPerSecond`
and the FOV keys are then ignored). `CTrackSim/Content/Lidar/mid360_pattern_2s.bin` is 2 s
(400 000 shots at 200 000/s, 4 lasers) recorded from a Mid-360 in its non-repetitive mode, every
shot including those without a return.

| key | default | |
|---|---|---|
| `PatternFile` | - | relative paths are looked up in the project's Content and project directories |
| `PatternPointsPerSecond` | file rate | lower values decimate the pattern in time (same angular coverage per second, fewer shots); capped at the file rate |
| `PatternFrameRate` | 10 | frames published per second (on average) |
| `UpdateFrequency` | 10 | in pattern mode: how often shots are fired; every firing traces the shots due since the previous one from the current pose (the settings use 50 Hz = 20 ms) |
| `MinRange` | 0 | hits closer than this are reported as misses |
| `Range`, `GenerateNoise`, `MinNoiseStandardDeviation`, pose | as before | |

Output per frame: every shot fired since the previous frame, in firing order, continuing through
the pattern across frames; shot i of n left at `time_stamp - (n - 1 - i) / pps`, so the frame starts
at `time_stamp - n / pps` (where the previous frame ended). Frame sizes vary by up to one firing's
shots (50 Hz: 16 800 or 21 000 shots, 20 000 on average). Misses and hits closer than `MinRange` are
NaN points (label `out_of_range`). Points are in the sensor frame (x forward, y right, z down). If the
pattern file cannot be loaded the sensor falls back to the rotating grid (frames of exactly
`NumberOfChannels x MeasurementsPerCycle` points, 16 x 512 by default) and logs an error.
Pattern file format: `"MID360PT"`, u32 version 1, u32 n_points, f32 points_per_second, u32 n_lasers,
then n_points x (f32 azimuth_deg, f32 elevation_deg), little endian, Livox frame (x forward, y left,
z up). `tools/check_mid360_pattern.py` checks a running sim against the file. The Cosys ROS2 bridge
keeps the order and the NaN points, converts to x forward, y left, z up (negates y and z), stamps
the PointCloud2 with `time_stamp` and marks it `is_dense: true` regardless.

## Vehicle look (S900) - not included
The Gazebo settings use an S900 octocopter look built by `CTrackSim/Scripts/make_s900_pawn.py`
from a 3D model that may not be redistributed, so the model and its imported assets are not in
this repository or the release build. Without them `run_unreal.sh` drops the pawn override and Cosys-AirSim uses its
default multirotor pawn; physics, sensors and poses are unchanged (only the look differs).
Note for the S900 pawn: its mesh has no collision, since the Cosys 3.5 lidar does not skip its own
vehicle and the -7 deg beams would hit the prop tips.

## Frames
Track frame (meters): origin = Start helipad, +X along the 100 m side, +Y toward the C lane, +Z up.
- Unreal: same axes; PlayerStart at the origin on the ground = AirSim NED origin.
- Gazebo (ENU): x = X, y = -Y, z = Z; the vehicle spawns at the origin facing +x.
- PX4 local NED: north = -Y, east = X.

## SLAM yard map
Source: a 2-minute handheld SLAMBOX recording (2026-10-12), exported with `sbox_export.py` at
10 cm voxels (5 cm drops too much: the "seen once" filter removes real geometry of a sparse scan).
`layout/slam_to_layout.py` then
- fits the ground plane (the scan is tilted 1.6 deg) and levels it to Z = 0,
- clusters the points above it on a 2D grid; buildings (taller than 10 m) become wall boxes along
  RANSAC line segments, trees are split at canopy-height peaks and get a trunk, a canopy lifted
  by `z` (bottom height) and, where present, undergrowth, from the vertical spread profile,
- with `--meshes`: voxel surfaces (close, fill, Taubin smoothing) of each canopy and object,
  trunk cylinders and a ground heightfield, written as `.obj` (Gazebo) and `.glb` (Unreal).
  `--collision mesh` (default) makes the meshes the colliders in both worlds, so the lidar sees the
  real shapes; the primitives they replace stay in the layout as `obstacles_primitive`.
  `--collision primitive` keeps them as hidden colliders under the meshes instead.

```bash
cd layout
python3 slam_to_layout.py slam/yard_map_points.ply yard_slam_layout.json --goal 18 47 \
    --preview yard_slam_layout.png --meshes meshes/yard
```
`--start` / `--goal` and the preview are in the SLAM frame (right-handed, origin = where the scan
started). The layout is in the track frame: X = SLAM x, Y = -SLAM y (Unreal is left-handed), so
Gazebo ENU equals the SLAM frame. START is the scan origin, 6 m or more from any obstacle; GOAL
(18, 47) is an open spot whose straight line from START crosses two trees.

Unreal import: `build_map_from_layout.py` imports each `.glb` with Interchange into
`/Game/CTrack/Meshes/Yard/`, sets complex-as-simple collision and compares the imported bounds with
the layout's `bounds` ("[mesh check]" warnings; all four match within 1 cm). Gazebo: about 0.36 M
collision triangles run at real-time factor 1.0; gzclient gets the GPU when `GUI=1`.

Ground: the relief (0.03-0.42 m above the fitted ground plane) is the ground in both worlds, so
vehicles stand and land on it and the lidar sees it. Unreal collides with the mesh; Gazebo with a
`<heightmap>` made from the same grid (`meshes/yard/ground_height.png`) - ODE's contacts between the
sloped triangles and the x8's thin skids flipped vehicles that landed on them. Gazebo 11 centres a
heightmap on the world origin whatever its `<pos>` x, y or the model pose say, so the image is
generated centred on (0, 0). Each waypoint gets a flat pad (2 m radius, 1.5 m blend; START at
0.03 m, GOAL at its relief, 0.17 m; `--pad-radius`), and `gen_gazebo_world.py` puts the relief
heights (`meshes/yard/ground_height.json`) next to the world as `ctrack.ground.json`, from which
`ctrack_sitl_entry.sh` starts the vehicle 0.5 m above the highest ground under it, wherever it is
spawned; it then drops onto the relief before arming. Spawn and land inside the scanned area: at
its border the relief can end in a step of up to 0.3 m down to the flat ground. To rebuild only the
ground (pads, heightmap) and its layout entry: `slam_to_layout.py ... --meshes meshes/yard --only-ground`.

Known limits: the north direction and GPS position of the scan are not registered yet; buildings
are facades only (no roofs); a few merged trees are still one mesh each.

To rebuild the yard map in Unreal (close Unreal first):
```bash
export CTRACK_MAP=Yard
UE=~/Downloads/Linux_Unreal_Engine_5.8.2/Engine/Binaries/Linux/UnrealEditor-Cmd
$UE "$PWD/CTrackSim/CTrackSim.uproject" -run=pythonscript -script="$PWD/CTrackSim/Scripts/create_base_map.py" -nullrhi -unattended   # once
$UE "$PWD/CTrackSim/CTrackSim.uproject" -run=pythonscript -script="$PWD/CTrackSim/Scripts/build_map_from_layout.py" -nullrhi -unattended
```
(`CTRACK_LAYOUT` overrides the layout file.) Flying in the yard: most trees are 4-5 m tall with the
canopy bottom at 2-3 m, so fly at about 2 m to avoid between trunks; START is the scan origin,
GOAL = track (18, -47). Altitudes are above the START pad (0.03 m); the GOAL pad is 0.14 m higher.

## Layout
`layout/ctrack_layout.json` lists what each object is and which values are assumed rather than
measured (`assumed`). Changes so far: the pole field is 1-2-3 rows of 0.5 m poles (X 66 / 56 / 46,
6 m apart) instead of the drawing's 2+1+2 field, so an x8 (prop tips 0.77 m) fits through and the
lidar resolves them at range.

After editing the layout, regenerate the Unreal map (close Unreal first; the commandlet saves it):
```bash
UE=~/Downloads/Linux_Unreal_Engine_5.8.2
$UE/Engine/Binaries/Linux/UnrealEditor-Cmd "$PWD/CTrackSim/CTrackSim.uproject" \
    -run=pythonscript -script="$PWD/CTrackSim/Scripts/build_map_from_layout.py" -nullrhi -unattended
```
Optional per obstacle: `z` (bottom height, default 0) and `visual: false` (hidden collider).
The Gazebo world is regenerated on every `run_gazebo_px4.sh`.

## Gazebo plugins
- `libctrack_wind_zone.so`: inside the box, drag F = 0.5 rho CdA |v_rel| v_rel on the vehicle
  (v_rel = wind - vehicle velocity). The PX4 x8 motor models have `enable_wind` off, so the stock
  `windy.world` wind does not act on the x8.
- `libctrack_moving_obstacle.so`: shuttles a kinematic model between two points; starts when the
  trigger model comes within `trigger_distance` of `trigger_point`.

## Patches to Cosys-AirSim 5.8-v3.5.0
- `0001` lidar: `DrawDebugPoints` drew from AirSim's physics thread, which asserts in UE 5.8;
  hit points are now drawn on the game thread (also fixes an out-of-range draw index).
- `0002` camera director: the "fly with me" view chases behind the vehicle along its heading.
- `0003` GazeboDrone: upstream applies the first entry of `~/pose/local/info` to the AirSim
  vehicle, but that order is not stable and moving obstacles appear in it. The vehicle is now
  selected by name (`GAZEBO_DRONE_MODEL`) and `GAZEBO_MIRROR_MODELS` are mirrored onto Unreal
  actors (simSetObjectPose).
- `0004` lidar: scan pattern mode (above).
- `0005` lidar output: frames are written by the physics thread and were copied by API / RPC
  threads without a lock, so a read could mix time stamp, points and labels of two frames (126 of
  22 000 reads with 20 000-shot frames). The latest frame is now an immutable snapshot swapped under
  a lock and copied outside it. Changes AirLib headers: rebuild AirLib (`setup_deps.sh`).

## Known issues
- GazeboDrone sometimes connected to AirSim but never received a Gazebo pose (lidar kept publishing
  from the spawn point). Gazebo transport advertised whichever external interface was up when each
  process started (LAN or Wi-Fi addresses seen); the container now pins it to `GAZEBO_IP=127.0.0.1`,
  and GazeboDrone is restarted if it prints no pose within 30 s.
